## 2. Правило 100%: як перевіряли

**Спосіб перевірки:** WBS побудовано на трьох рівнях: корінь проєкту, шість основних напрямів і конкретні пакети робіт. Для кожного батьківського вузла перевірено, що сума годин дочірніх пакетів дорівнює його оцінці. Загальна трудомісткість становить 1200 годин, або 71,4% доступної місткості команди (1680 годин).

Повноту декомпозиції перевірено за складом першого релізу `REL-1` у беклозі та основними етапами життєвого циклу проєкту: управління, аналіз вимог, UX/UI, розробка, тестування та впровадження. Пакети робіт не дублюються між напрямами.

**Робота, яку ледь не забули:** під час перевірки повноти WBS окремо враховано підготовку середовища розробки (`1.4.1`), налаштування доступу та ролей (`1.4.2`), приймальне тестування (`1.5.3`) і підготовку документації та передачі системи (`1.6.2–1.6.3`). Ці роботи не завжди представлені окремими користувацькими історіями, але необхідні для випуску працездатного продукту.

**Що свідомо поза обсягом:**

- Повноцінна інтеграція з усіма внутрішніми системами академії — перший реліз передбачає імпорт розкладу з погодженого джерела даних.
- Окремий вебзастосунок для адміністрації — пріоритетом є мобільний застосунок для перегляду розкладу.
- Платіжна система та платні підписки — не потрібні для реалізації основної мети проєкту.
- Розширена аналітика відвідуваності й успішності студентів — не належить до основних функцій першого релізу.

Наведені обмеження деталізують межі першого релізу. Їх необхідно узгодити з розділом «не робимо» статуту `lr05_charter/README.md`, щоб обсяг проєкту залишався послідовним в усіх артефактах.
